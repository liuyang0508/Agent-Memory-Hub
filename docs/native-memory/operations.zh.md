# 组织原生记忆运行与恢复

本页描述当前单节点实现。部署模板在 `deploy/native-memory/`；生产部署、域名/TLS 和四端真实环境需独立验收。多节点限制见 [架构说明](architecture.zh.md)。

## 管理后台登录

Hub 1.4.2 支持飞书身份认证与明确管理员角色；首次授予、撤销和应急入口见[后台登录说明](admin-login.zh.md)。

## 观测入口

| 入口 | 能说明什么 | 不能说明什么 |
|---|---|---|
| `GET /native/v1/health` | HTTP 进程存活、协议版本兼容 | 数据库正常、资产可召回 |
| `GET /native/v1/ready` | 数据库存在、schema/索引可访问、当前可取得写锁；异常返回503 | 全库完整性、剩余磁盘、远端用户网络可达 |
| `amh-native status` | 本地身份概要、待传计数、最近同步/错误 | 当前产品模型已经读到资料 |
| 状态目录 `status.json` | 最近同步数量、冲突或失败类型 | 历史所有错误的完整审计 |
| Hook 事件诊断 | remote/cache/unavailable 等路径、注入大小 | 凭借一次缓存命中证明实时云端满足性能要求 |
| `amh-native recall-trace` | 本设备最近召回的候选、入选、送达状态与各阶段名次 | 模型是否采用了注入内容（「模型已收到」有回执依据，「回答已采用」靠人工反馈） |
| `GET /native/v1/admin/recalls` | 全组织召回记录与投递状态（管理令牌） | 同上；问题文本可用 `recall_query_preview=off` 关闭 |
| `GET /native/v1/admin/insights` | 按天汇总的召回使用情况：投放漏斗、各通道/成员次数、降级与丢弃原因、哪些记忆被注入给了谁、跨成员复用、无结果的提问；原始明细过期后汇总仍保留 | 「已引用」只有显式反馈，没人打就是零；MCP 侧的读取、送达、引用不可观测；汇总起始日之前的使用情况一律不可观测 |

监控至少关注持续 readiness 失败、待传队列增长、最近成功同步时间、原生投放冲突、磁盘空间和 TLS 到期。当前没有内置监控平台或通知发送器。不要记录设备令牌、邀请、用户问题及记忆正文作为普通诊断信息。

短暂锁竞争允许重试。readiness 失败不应直接触发进程不断重启；liveness 与 readiness 分开使用。数据异常必须排查/恢复，不能靠删除数据库“修复”。

`amh-native hook-stats` 汇总最近若干天的这些记录。`hook-metrics.jsonl` 每行还记录 `retrieval`（`hybrid` 或 `lexical`）、被跳过的提示记为 `mode: skipped` 和 `reason`，以及 `via`（`service` = 常驻 worker 的热连接，`worker` = 临时子进程）和 `budget_ms`（本次总预算）；`elapsed_ms` 贴着 `budget_ms` 且 `mode` 为 `unavailable`，说明链路往返超过预算，用 `amh-native recall-timeout` 查看或调整。

## 语义检索（1.4.7 起）

Hub 用本地 ONNX 模型做语义检索，不依赖 PyTorch，不在运行时联网。部署脚本按 `deploy/native-memory/semantic-model.json` 固定的仓库、修订和每个文件的 sha256 准备模型：GitHub 部署流水线在 Hub 缺少已校验的副本时代为下载并随包上传（Hub 主机访问不了 huggingface.co），手工执行 `upgrade.sh` 时依次尝试同目录 `model/`、`AMH_HF_ENDPOINT`、hf-mirror.com、huggingface.co。任何一步失败都不阻断升级，Hub 保持仅词法检索。模型目录 `/opt/amh-native/models/<名称>@<修订前12位>`，环境文件 `/etc/amh-native/semantic.env`。

当前模型 jina-embeddings-v2-base-zh（int8，约 160 MB，中英双语，Apache-2.0）。选型依据：在组织记忆副本上用 55 条有答案、12 条无答案的中文提问对比了 9 个模型；仅词法时首位命中 65%、前三 76%，无答案的提问 12 条全被注入内容；该模型加召回门控后首位 85.5%、前三 98.2%，无答案的提问只有 2 条被注入。常驻内存约增加 400 MB；同等准确率的 gte-multilingual-base 和 bge-m3 需要 0.8–1.1 GB，在 2 GB 内存的主机上不采用。

- 索引由 `serve` 自己维护：启动 30 秒后首轮全量编码，之后每 120 秒只编码新增或改动的记忆与规则（`--semantic-interval` 可调）；没有变化时不写库。
- `GET /native/v1/health` 的 `semantic.state` 为 `ready` 时出现 `semantic-v1` 能力；`loading` 表示首轮未完成，`unavailable`/`error` 表示退回仅词法，原因写在召回明细的 `reasons` 里。
- 召回门控只作用于提示时 Hook 通道：相似度低于下限（默认 0.40）或比最高分低出 0.08 的候选不注入；提示里的字面标识符（错误码、函数名、带下划线或点的词）在词法前三命中时保留。MCP 检索不过门控。阈值来自模型清单，可用 `AMH_NATIVE_HOOK_MIN_SCORE`、`AMH_NATIVE_HOOK_MARGIN` 覆盖，改阈值不触发重建索引。
- 跳过语义：在部署机器上设置 `AMH_SEMANTIC=off` 再执行 `upgrade.sh`。
- 其他 Hub（例如 platform.linkcrux.com）不在本仓库的部署流水线里，需要有权限的人在那台机器上用同一个 `upgrade.sh` 升级；Hub 能访问 hf-mirror.com 或把模型文件放在脚本同目录的 `model/` 下即可。

## 召回相关性、评测与校准（1.4.9 起）

### 设计原则

1. **主动推送宁缺毋滥，按需查询保证查全。** Hook 是成员没开口就塞进对话的内容：注入一条无关记忆会分散注意力、还可能把模型带偏；漏掉的内容模型可以用 `search_org_memory` 主动查回来。所以 Hook 只注入「大概率相关」的少数几条，MCP 检索不过门控。
2. **多路证据互相印证，不靠单一阈值。** 语义相似度在 0.40–0.50 区间里相关和无关严重重叠。门控综合 8 个信号（相似度、与本题最高分的差距、这条记忆对日常提问的「背景相似度」、这个提问对全库的泛化程度、关键词名次、是否索引文件、提问内容词覆盖率、字面标识符），用逻辑回归估计「相关的概率」。背景相似度是向量检索里处理「枢纽文档」（hubness，几乎和什么都像的文档）的 CSLS 局部尺度校正思路，背景用一组固定的、不含组织知识的通用提问。
3. **调参和报分不用同一批数据。** 阈值用按问题分组的 5 折×5 次交叉验证选：每一折的模型都没见过它要判的问题。各阈值的效用相差不到一个标准误时视为打平，取最低的阈值（一倍标准误规则），打平时不牺牲召回。
4. **一份记忆只占一个名额。** 同一笔记从多个产品或设备上传、或索引文件按不同边界切分时，正文互相包含度 ≥ 0.5 的只保留排名最高的一份。
5. **每一步都可见、可追溯。** 召回表格的「相关」列就是模型给出的相关概率；Hub 的召回明细里每个候选都有 `gate.probability` 和被拦下的原因（`relevance_gate`、`near_duplicate`）。

### 当前效果

2026-11-04 在组织记忆副本（91 份记忆与规则）和 105 题问题集（77 题有答案，其中 22 题是真实口吻的长提问；28 题没有答案，其中 16 题是日常工作提问）上，交叉验证结果：

| 门控 | 首位命中 | 前三命中 | 注入内容中相关的比例 | 无答案时不注入 | 每次注入 |
|---|---|---|---|---|---|
| 1.4.7 阈值门控 0.40/0.08 | 85.7% | 92.2% | 56.6% | 64.3% | 2.87 条 |
| 1.4.9 学习式门控（阈值 0.30） | 87.8% | 91.4% | 74.4% | 75.0% | 1.56 条 |

真实口吻的长提问首位命中 86%→95%，注入内容中相关的比例 55%→84%。剩下最难的是和某条记忆字面上真有重合的日常提问（例如「表格没渲染成功」和 PPT 表格渲染那条记忆），这类只能靠使用反馈继续改进。

### 运行方式

- 门控模型随语义模型清单发布（`semantic-model.json` 的 `manifest.hook_gate`），`upgrade.sh` 写入模型目录；改门控不触发重建索引。`AMH_NATIVE_HOOK_GATE=/path/gate.json`（写进 `/etc/amh-native/semantic.env`）可覆盖清单。
- `serve` 每轮索引维护时预热通用提问库（60 条，几秒）；预热完成前 Hook 退回 1.4.7 的阈值门控，召回明细 `reasons` 里有 `gate_background_pending`。
- `GET /native/v1/health` 的 `semantic.gate` 显示门控版本（`learned-v1`、`on` 表示旧阈值门控、`off`），学习式门控生效时出现 `relevance-gate-v1` 能力。

### 评测与重新校准

问题集是 JSON 列表或 JSONL，每题 `{"id", "query", "expect": [路径/标题/正文片段], "tags": [...]}`，`expect` 为空表示「这题不该注入任何记忆」。按 id 稳定分成 dev 和 test，也可以在题目里写 `split`。问题集含组织内部内容，只放在 Hub 主机或公司目录里，不进开源仓库。

```sh
# 在 Hub 主机上（数据不出服务器；在数据库快照上运行，不写召回记录）
amh-native recall-eval --db /var/lib/amh-native/hub.sqlite --gold gold.json \
  --out report.json [--baseline last-report.json]        # 退步超过 0.02 时退出码 1
amh-native recall-calibrate --db /var/lib/amh-native/hub.sqlite --gold gold.json --out gate.json
```

报告给出首位/前三命中、MRR、注入内容中相关的比例、无答案时不注入的比例、平均注入条数、时延 p50/p95，以及 95% 自助法置信区间，并按 dev/test 和标签拆分。题少的时候先看置信区间，再判断变化是否真实。建议：语料明显增长、换模型或成员反馈召回不准时，补充真实提问后重新校准；新门控先用 `recall-eval --baseline` 和旧报告对比，没有退步再上线。

## 使用反馈与每周自动校准（1.4.11 起）

问题集是组织写下的「标准答案」，但题目有限，也跟不上语料的变化。使用反馈补上这一块：每一次真实的召回之后，记忆有没有被用上。

### 反馈怎么来

- **判断在成员本机做。** 每轮回答结束时（Stop Hook），客户端把这轮注入的记忆和模型的输出（回答文字和工具调用）对比。只有既不在提示里、也不在本会话更早内容里、也不在本轮工具结果里的内容才算证据，这样「同一个项目的常用词」不会被误当成用上了。
- **宁可不标，不标错。** 出现长的具体标识（路径、命令参数、带版本的名字），或者三段以上独立的原文，才标「用上了」；完全没有交集才标「没用上」；其余不标。模型自己用 `read_org_memory` 查到、并用上了一条门控拦下的记忆，标「自己查来用了」，这是门控漏召的直接证据。
- **只上报编号和标签。** 提示到回答结束之间，本机只保存记忆内容的加盐摘要，不存正文；发给 Hub 的只有 asset id、版本和标签。Claude Code 之外（看不到更早的会话内容），只上报「没用上」。
- **核验（已核实）：** 在本机 88 轮真实 Claude Code 会话、195 次注入上，判出「没用上」117 次，抽查 39 次全部正确；「用上了」1 次，正确；19 次不标。同一批数据里，58 次注入由后台任务通知触发，1.4.11 起这类事件不再召回。

### 每周校准怎么决定上不上线

Hub 把每个标签连同召回当时门控看到的 8 个信号数值存下来（`recall_labels`，只有数字，保留 180 天），`serve` 每周为每个有问题集的组织跑一次：

1. **反馈只教，不判分。** 新门控在「问题集 + 使用反馈」上拟合。反馈按类别平衡加权，总权重最多是问题集候选数的一半，避免某一个人的大量反馈压过问题集。阈值仍然只按问题集的交叉验证选。
2. **两道检查都过才启用。**
   - 问题集上有提升、不退步：两种做法（只用问题集、问题集加反馈）用同样的分组交叉验证打分。新做法的综合分不能下降（没有提升就不换，避免来回变）；首位命中、相关比例、拒答率可以互相让一点，但都不能低 0.02 以上。
   - 真实使用上不能明显更差：每类反馈最新的四分之一留出不参与训练，新门控给这些样本排序的 AUC 可以比线上门控低，但不能超过抽样误差（配对自助法估计，至少 0.02）。几十条留出反馈证明不了「更好」，但能发现「明显更差」。
3. **可追溯、可回退。** 每次运行都记下结论和数字，不管启用没有。启用的门控按组织保存，并绑定当时的语义模型（换模型后自动回到清单门控）；`AMH_NATIVE_HOOK_GATE` 仍是运维的最终指定。

**离线模拟（已核实，组织记忆副本、105 题问题集）：** 把问题集随机对半分，一半当「真实使用」：线上门控注入的记忆按是否相关标成用上或没用上，并故意翻转 0%、10%、30%、50% 的标签；被拦下的相关记忆有 30% 当作「自己查来用了」。另一半当问题集做检查。3 种分法 × 4 种噪声共 12 组：

| 结论 | 组数 | 问题集综合分 | 首位命中 |
|---|---|---|---|
| 启用 | 6 | 全部上升，+0.6 到 +5.9 个点 | 没有一组下降 |
| 问题集退步而拒绝 | 5 | 有的上升 | 下降 3.8–6.5 个点，或相关比例下降 2.8 个点 |
| 真实使用明显更差而拒绝 | 1 | 上升 | AUC 低 0.067，超过抽样误差 0.045 |

推断：即使「用上 / 没用上」完全随机（50% 翻转），启用的那些组综合分也在上升，靠的是「自己查来用了」这类漏召证据，以及问题集守门。问题集守门是主要的安全保障；留出反馈只能发现明显更差的情况，题量小时证明不了提升。

至少要有 30 条反馈，「用上了」（含自己查来用了）和「没用上」各至少 5 条，问题集至少 20 题、其中至少 10 题有答案，否则这次运行只记录「数据不够」。

### 操作

```sh
# 成员本机
amh-native recall-gold-upload --gold gold.json      # 补充组织问题集（id、query、expect、tags）
amh-native recall-tuning                            # 反馈条数（7 天/30 天）、上次结论、门控版本历史
amh-native recall-tuning --run                      # 现在就在 Hub 上跑一次（每小时最多一次）

# Hub 主机（在数据库快照上计算，通过检查才写回）
amh-native recall-autotune --db /var/lib/amh-native/hub.sqlite            # 只评估
amh-native recall-autotune --db /var/lib/amh-native/hub.sqlite --apply    # 通过则启用
amh-native recall-autotune --db /var/lib/amh-native/hub.sqlite --rollback # 退回上一版
```

`serve --autotune-days 0` 关闭每周校准。`amh-native recall-trace --trace <id>` 会显示每个候选这一轮是否被用上。

## 一键安装与升级 Hub（1.4.16 起）

在 Hub 主机上以 root 运行一条命令，首次安装和升级都用它：

```sh
curl -fsSL https://github.com/liuyang0508/agent-memory-hub/releases/latest/download/hub.sh | sudo bash
# 指定版本：… | sudo bash -s -- --version 1.4.16    国内强制走镜像：--cn    不装语义模型：--no-semantic
```

脚本按以下顺序执行，任何一步失败都会停下：

1. 找可用的 Python（3.11–3.13）。
2. 下载发布包，逐个核对校验和。
3. 准备依赖：访问不了 PyPI 时自动改用清华镜像。
4. 备份数据库。
5. 升级：语义模型从 hf-mirror 下载并核对，原子切换，失败自动回滚。
6. 处理旧配置：如果 drop-in 里写死了旧模型路径，等新模型就绪后注释掉那一行。原文件备份为 `*.bak-<版本>`；如果之后服务起不来，会自动恢复。
7. 收尾：等语义检索建完索引，打印版本、模型、门控和能力列表。

GitHub 访问慢时，用 `AMH_RELEASE_BASE` 指向内部镜像，目录结构保持 `v<版本>/文件名`。Hub 升级后，各成员客户端会在一天内自动跟到同一版本。

**主机访问不了 Hugging Face 时（1.4.17 起）**：模型下载失败，脚本结尾会用黄字写明「semantic recall is NOT running」，并列出要下载的模型文件地址、存放路径和 sha256。在能访问的机器上按列出的路径下好，放进同一个目录，拷到 Hub 主机上，然后重跑脚本：

```sh
sudo bash hub.sh --model-dir /path/to/model-dir      # 目录内：tokenizer.json、onnx/model_int8.onnx
```

文件仍按 sha256 核对。等待建索引时，如果 Hub 报告模型加载失败，健康检查的 `semantic.state` 会是 `unavailable`，`reason` 写明原因，脚本立即结束，不再空等 30 分钟。

## 召回分档与上文补充（1.4.18 起）

提问时召回分三档：

| 档位 | 条件 | 注入什么 |
|---|---|---|
| 全文 | 门控概率达到阈值，**且**语义领先量 ≥ 0.08 | 记忆正文 |
| 只给标题 | 没进全文档，但概率 ≥ 0.15 且语义领先量 ≥ 0.04，最多 2 条 | 一行标题 + asset_id + revision，模型需要时用 `read_org_memory` 读 |
| 不给 | 其余 | 无 |

- **语义领先量**：这条记忆与本次提问的相似度，减去它与一组日常提问（写代码、翻译、闲聊等）的平均相似度。领先量小，说明这条记忆对什么问题都"看起来相关"，实际上并不针对这次提问。门控里的"排第一""最接近"都是相对量，在记忆少的组织里总会有一条排第一；这道门槛防的就是这种情况。提问里的具体标识（路径、错误码、版本号等，不含 500 这类状态码、年份和 MEMORY.md 这类通用文件名）整词出现在记忆中时，门槛放宽到概率 ≥ 0.1 且领先量 ≥ 0。
- 数值来自两个组织记忆库（94 条和 34 条）上的 105 题问题集，分组交叉验证 25 次中有 23 次选中 0.08。在没参与调参的题上：拒答率 75%→89%、43%→89%；第一条命中率 88%→87%、61%→57%。
- 每周自动校准会把这套规则带进新门控；手动校准用 `recall-calibrate --lift --hint-threshold --hint-lift`。
- **上文补充**：Claude Code 里，16 个字以内、不带标识的短句（如「那第二个呢」），检索时会带上同一会话 30 分钟内的上一句提问。结果只给标题、不注入正文，因为找到的可能属于上一个话题。召回表会注明「上文补充」。

## 经营驾驶舱（1.4.20 起）

`/native/v1/admin/dashboard` 是面向管理者的总览，飞书管理员或管理令牌可看，不含记忆正文。原「数据看板」「记忆洞察」合并到这里，`/admin/insights` 地址仍可访问。

- **怎么读**：先看经营结论和待决事项（只列需要决策的事，每条带依据和建议动作），再看平衡计分卡，最后看明细。
- **状态对照的是默认管理基准，不是组织目标**，口径见页面「指标口径与默认管理基准」。
- **北极星指标是"记忆被真正用上"的次数**，来自使用判定，需要客户端 1.4.11 以上；没有判定时显示注入次数并注明。
- **页面不估算节省的工时或金额**，没有数据能支撑。
- 团队协作部分用来发现协作机会和关键人风险，不作绩效考核依据。

## 密钥与误传处理（1.4.20 起）

- 会话记录只把疑似密钥的片段打码（`[已隐去:类别]`），其余照常同步。记忆、规则、skill、配置含密钥则整份不上传，已入队或已上传的部分会撤回，文件名和类别记在 `amh-native status` 的 worker 状态里；修好后自动恢复同步。升级后第一轮会对已同步的文件重查一遍。
- **筛查只认得有固定特征的密钥和"密码是…"这类写法。** 单独一串看不出是密码的字符识别不了；如果成员开启了会话记录同步，在聊天里发过的密码要按已泄露处理，尽快更换。
- 修改或删除记忆后，旧版本的正文从变更日志中清除，只留元数据。升级后 Hub 在后台分批清理历史数据，不影响服务，中断后下次启动继续；数据库文件不会变小，空出的空间留给之后的写入。
- 驾驶舱「系统健康」会列出 Hub 上疑似含密钥的记忆（只有名称和类别）。处理步骤：让作者修好源文件并**更换泄露的密钥**，然后在 Hub 主机执行：

```sh
sudo -u amh-native /opt/amh-native/current/venv/bin/amh-native purge-asset --db /var/lib/amh-native/hub.sqlite --asset-id <编号> --yes
```

成员本机如果开启过投影（默认关闭），已同步的副本要在本机另行清理。

1.4.21 以前留在数据库空闲页里的旧内容，后台清理碰不到。发生过泄露时，等驾驶舱不再报告、后台清理结束后，在维护窗口运行一次 `amh-native compact --db /var/lib/amh-native/hub.sqlite --yes`（期间写入被阻塞）。

## 语义不可用时的召回保护（1.4.17 起）

Hub 没有语义检索时（模型没装好、加载失败或索引没建完），学习门控无法打分。这时如果按关键词照常注入，任何与提问有一个词重合的记忆都可能被塞进对话。因此提问时的召回（hook）改为保守模式：

- 只注入「提问里的标识原样出现在记忆中」的条目，例如文件路径、错误码、版本号、`snake_case` 或 `camelCase` 符号、链接；而且必须是关键词排名前 3 的条目，最多 2 条。
- 其余候选不注入，记录在召回轨迹里，原因写 `lexical_guard`；召回表的表头会注明「只注入含提问中标识的记忆」。
- 模型主动调用的检索工具（`search_org_memory`）不受影响。
- 需要恢复旧的纯关键词注入时，在 Hub 的环境里设置 `AMH_NATIVE_HOOK_LEXICAL_GUARD=0`。

## 客户端自动升级（1.4.14 起）

- 升级顺序只需要管 Hub：Hub 升级后，各成员的常驻后台进程在 24 小时内（启动后 2–15 分钟内首次检查）自动升到 Hub 的版本。Hub 的健康检查返回 `version`，客户端不会超过它。
- 安装包来自项目发布页，必须和该版本的 `checksums.txt` 一致；装完由新进程导入并核对版本号，不通过就装回原版本。每台机器只由开着召回的那个档案执行，多个档案共用一把锁；装好后后台进程原地重启到新代码，其他档案在一分钟内发现版本变化后也重启。
- 发布页在内网不可达时，可以设置 `AMH_UPDATE_BASE`（或档案配置 `update_base`）指向内部镜像，目录结构保持 `v<版本>/文件名`。
- 早于 1.4.14 的 Hub 不返回版本，连接它的客户端保持现有版本。

## 故障处理

| 故障 | 当前行为 | 运维动作 |
|---|---|---|
| 网络断开、408/429/5xx | 保留 outbox，停止本批，后台退避并抖动重试 | 检查 URL/TLS/网络和 Hub readiness；恢复后确认队列收敛 |
| 401/403 | 明确拒绝，清理受管理缓存/投放，不按普通离线错误回退 | 确认设备撤销状态；需要时重新登记，不能改名伪装原设备 |
| 记录版本冲突 | 保留待传记录；下载自身变更修复基础版本后重试 | 持续冲突检查来源拥有者和历史；不要强行覆盖他人资产 |
| 本地文件被人工编辑 | 投放报告冲突并保留编辑 | 对照拥有权清单/来源决定保留或重新投放 |
| Cowork 配对过期/首次运行无状态 | 正常任务继续，组织记忆暂不就绪 | 重新运行 `cowork-connect`，把独立连接文件放入该运行时可访问的目录；不要把邀请贴进聊天 |
| Cowork Hook 的 cwd 为 `/private/var/empty`、插件数据位于临时目录 | 工作目录找不到连接文件；临时状态不能保证跨会话复用 | macOS 宿主模式用 `cowork-connect --runtime-state <持久目录>` 重新生成并导入包，同时固定外部连接文件路径；不要把宿主机路径复制给 VM/云任务 |
| Cowork 目录身份变化 | 来源被隔离，不扫描、不上传、不投放到该目录 | 核对项目/挂载身份；用独立状态重新登记来源并预览历史，保留旧状态对账。当前不自动解除隔离，不能直接清标记强行共享 |
| 进程意外退出 | 未提交事务回滚；队列与游标留在磁盘 | 启动同一 profile，确认正常同步；不要并行重建多个身份 |
| Hub 主机/磁盘故障 | 默认云端召回不可用；显式投放模式的有限缓存和已有原生文件仍可能可读 | 恢复已验证备份并处理备份之后的撤销及变更；当前无自动切主 |

Hook 离线授权窗口只约束 Hook 缓存消费；已同步到原生文件或当前模型上下文的资料无法保证即时撤回。暂停也不等于删除已有共享内容。

## 备份与恢复

1. 使用 SQLite `Connection.backup()` 对运行库做一致快照；不要只复制主文件而忽略 WAL。备份与线上目录隔离，采用私有文件权限。
2. 在隔离路径打开快照，执行 `PRAGMA integrity_check`，核对组织、成员、设备、资产和变更数量，检查已知查询和删除记录。仅“文件存在”不算备份可恢复。
3. 备份可能早于设备撤销。恢复前对账撤销状态；无法对账时先隔离访问并使不确定凭证失效，重新发放邀请。
4. 恢复旧快照会使服务端变更序列倒退，而客户端可能持有更高游标及旧副本。当前协议没有自动识别 Hub 恢复代次的能力：不能直接恢复后放流并宣称客户端已收敛。先隔离旧 endpoint，使用新的 profile 重新登记/完整同步，并对新来源历史做预览选择；保留旧状态用于对账，不直接清空客户端库。
5. 在隔离服务完成两成员的上传、查询、删除、拒绝访问和原生读取测试，再按部署边界决定切流。先停止原进程、保留原文件和配置，验证恢复路径后才切换。

自动故障切换需要额外的恢复代次/游标重新对齐机制，属于架构文档中的后续高可用实现，当前不能靠代理配置代替。

## 实机验收隔离

使用独立 `CODEX_HOME`、`CLAUDE_CONFIG_DIR` 和 AMH `--state`，先验证真实客户端能加载配置，再验证 Hook、模型消费及关闭路径的对照。测试不默认修改日常 `~/.codex` / `~/.claude` 配置。桌面 UI 必须在独立实例/配置中验证；引擎测试不能替代 UI 结论。

记录验收资料的原始生产成员、产品和文件，不把脚本写入的合成记录说成模型生成。当前 CLI 实机证据是显式请求原生记忆写入与消费，不覆盖所有后台自动提炼触发条件。
